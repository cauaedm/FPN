# 2.3.2 Arquitetura da Solução e Tecnologias Utilizadas

## Visão Geral

A solução implementada adota uma arquitetura de **site estático gerenciado por conteúdo**, na qual os dados dos projetos de extensão são armazenados em arquivos de configuração versionados e o portal web é gerado automaticamente a partir deles. Essa abordagem elimina a necessidade de banco de dados relacional e de infraestrutura de servidor de aplicação, reduzindo custos operacionais e aumentando a confiabilidade e segurança do sistema.

A arquitetura é composta por quatro camadas principais, conforme ilustrado a seguir:

```
┌─────────────────────────────────────────────────────────────┐
│                     Administrador/Editor                    │
│         (edita arquivos YAML via repositório Git)           │
└────────────────────────────┬────────────────────────────────┘
                             │ git push
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                    GitHub Actions (CI/CD)                   │
│   1. Checkout do repositório                                │
│   2. Build com Hugo (geração do HTML estático)              │
│   3. Deploy via rsync para o servidor da UFRJ               │
└────────────────────────────┬────────────────────────────────┘
                             │ rsync over SSH
                             ▼
┌─────────────────────────────────────────────────────────────┐
│               Servidor Web da UFRJ (ic.ufrj.br)             │
│          Serve os arquivos HTML/CSS/JS estáticos            │
└────────────────────────────┬────────────────────────────────┘
                             │ HTTP
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                     Usuário (Discente)                      │
│          Acessa ic.ufrj.br/info/projetos-extensao/          │
└─────────────────────────────────────────────────────────────┘
```

## Tecnologias Utilizadas

### Hugo (Gerador de Site Estático)

**Hugo** é um gerador de site estático de código aberto escrito em Go, reconhecido por sua velocidade de compilação e flexibilidade de templating. A versão mínima adotada no projeto é a **0.149.1**.

**Justificativa de escolha:** O site oficial do IC já utiliza Hugo como plataforma. Integrar a página de extensões ao mesmo ecossistema dispensa a implantação de qualquer nova infraestrutura de servidor e mantém consistência visual e operacional com o restante do portal institucional.

**Papel na solução:**
- Lê os dados dos projetos de extensão a partir de arquivos YAML (`data/extensoes.yaml`) em tempo de build.
- Renderiza o portal de extensões através de um *shortcode* (template HTML reutilizável), gerando HTML estático com todos os campos exigidos por RF12 e RF18.
- Produz o arquivo HTML final em `public/info/projetos-extensao/index.html`, servido diretamente pelo servidor web da UFRJ.

**Referência:** https://gohugo.io

---

### YAML (Camada de Dados)

Os projetos de extensão são persistidos no arquivo `data/extensoes.yaml`, seguindo um esquema estruturado com os campos definidos pelos requisitos funcionais RF03, RF12 e RF18:

| Campo | Tipo | Descrição |
|---|---|---|
| `titulo` | string | Nome do projeto |
| `coordenador` | string | Nome do(a) coordenador(a) |
| `area` | string | Área temática principal |
| `modalidade` | string | Modalidade da extensão (ex.: Projeto, Curso) |
| `carga_horaria` | inteiro | Carga horária semanal em horas |
| `descricao` | texto | Descrição das atividades previstas |
| `vagas` | inteiro | Quantidade de vagas disponíveis |
| `bolsa` | booleano | Presença de bolsa (true/false) |
| `processo_seletivo` | string | Forma de seleção dos participantes |
| `perfil` | string | Perfil desejado do candidato |
| `contato` | string | E-mail de contato do coordenador |
| `link_inscricao` | string | URL para inscrição ou mais informações |
| `ano_inicio` | inteiro | Ano de início do projeto |
| `ano_fim` | inteiro | Ano de encerramento (omitido se ainda ativo) |

**Justificativa de escolha:** YAML é um formato de texto simples, legível por humanos e amplamente suportado. Por ser versionado no mesmo repositório Git do site, qualquer alteração nos dados dos projetos é rastreável, auditável e revertível, o que atende ao requisito de governança do Comitê de Extensão do IC (RF08, RF17).

---

### Go HTML Templates / Shortcodes (Camada de Apresentação)

O Hugo utiliza a linguagem de templates padrão do Go para renderizar HTML. No contexto deste projeto, foi implementado o *shortcode* `extensoes` (`layouts/shortcodes/extensoes.html`), que:

1. Lê todos os registros de `data/extensoes.yaml`.
2. Separa projetos **ativos** (sem `ano_fim`) de **encerrados** (com `ano_fim` definido), atendendo a RF21.
3. Ordena os projetos por ano de início, do mais recente ao mais antigo.
4. Renderiza um cartão (`card-extensao`) para cada projeto, exibindo todos os campos obrigatórios de RF18.
5. Aplica o indicador visual "Sem vagas no momento" quando `vagas` é zero ou ausente (RF20).

O shortcode é ativado na página de conteúdo com a diretiva `{{< extensoes >}}`.

---

### CSS Customizado (Camada de Estilo)

A aparência dos cartões de extensão segue o *design system* do tema institucional `temaic`, utilizando as variáveis CSS já definidas (paleta de cores do IC, tipografia, bordas). Foram adicionadas ao arquivo `themes/temaic/static/css/style.css` as seguintes classes específicas:

| Classe CSS | Propósito |
|---|---|
| `.lista-extensoes` | Container em lista vertical dos cartões |
| `.card-extensao` | Cartão individual de um projeto |
| `.card-extensao-concluido` | Opacidade reduzida para projetos encerrados |
| `.extensao-area` | Badge colorido com a área temática |
| `.extensao-metadados` | Grade de pares chave-valor dos metadados |
| `.sem-vagas` | Texto em vermelho para projetos sem vagas (RF20) |
| `.extensao-perfil` | Destaque lateral para o perfil desejado |

### GitHub Actions (CI/CD)

O pipeline de integração e entrega contínua é definido em `.github/workflows/deploy.yml` e é acionado automaticamente a cada `git push` na branch `master`. O fluxo executa três etapas em sequência:

1. **Checkout** — clona o repositório completo, incluindo o submódulo do tema `temaic`.
2. **Build** — executa `hugo --minify`, gerando os arquivos HTML/CSS/JS otimizados em `public/`.
3. **Deploy** — transfere o diretório `public/` para o servidor da UFRJ via `rsync` sobre SSH, utilizando credenciais armazenadas como *secrets* do repositório GitHub.

**Justificativa de escolha:** A adoção de CI/CD elimina etapas manuais de publicação, garantindo que toda alteração nos dados ou no template seja propagada ao site institucional de forma automática e auditável — o que atende diretamente ao requisito RF12 (Atualizar informações do site).

---

### Repositório e Controle de Versão (Git / GitHub)

Todo o código-fonte, templates e dados dos projetos de extensão são versionados em um repositório Git hospedado no GitHub. Essa decisão de projeto confere:

- **Rastreabilidade:** cada alteração nos projetos é registrada com autor, data e mensagem de commit.
- **Reversibilidade:** é possível desfazer qualquer publicação incorreta com um simples `git revert`.
- **Colaboração:** membros do Comitê de Extensão do IC podem propor alterações via *pull requests*, submetendo-as a revisão antes da publicação (suporte ao fluxo de governança do RF08).
